요즘 로컬 LLM 쪽이 정말 빠르게 발전하고 있습니다.
특히 온디바이스(On-Device)를 타겟으로 한 초경량 모델들이 쏟아지고 있는데, 그 중에서 350M이라는 초경량 규모의 SLM을 발견했습니다.

![](/media/2026-04-03-lfm2-350m-test/figure1.png)

이름에서 알 수 있듯이 파라미터가 고작 **3억 5천만개**입니다. 요즘 나오는 모델들이 billion 단위인 걸 생각하면 정말 작은 모델이죠.


사실 저는 이전에도 초경량 모델을 파인튜닝하고 사용해본 경험이 있습니다. 하지만 초경량 모델 사용에 대한 내용이 아닌 [삽질하며 Gemini와 씨름하던 내용](/posts/gemini-review-im-fine-and-you)이 위주였습니다.<br>
저 당시엔 Gemma3 270M으로 상당히 빨랐고, 제 컴퓨터 스펙으로도 파인튜닝이 가능해서 꽤 재밌게 진행했던 기억이 납니다.
그렇게 경제 기사 읽고 어느 종목에서 호재인지 알려주는 정도의 작업이 가능했으나, 270M이라서 성능이 많이 부족한터라 판단 사유가 꽤 이상하게 나오곤 했습니다.


근데 이 친구가 기존 초경량 중 꽤 잘 한다는 소문이 있어서, 직접 오라클 클라우드 무료 티어 ARM 서버에 올려서 이것저것 테스트해봤습니다.

## 테스트 환경

| 항목 | 스펙 |
|------|------|
| **서버** | Oracle Cloud 무료 티어 (Ampere A1) |
| **CPU** | ARM 4 OCPU |
| **RAM** | 24GB |
| **GPU** | 없음 (순수 CPU 추론) |
| **프론트엔드** | Open WebUI |
| **백엔드** | Ollama 0.19.0 |
| **모델** | LFM2.5-350M (Q8_0 양자화) |
| **모델 크기** | 약 450MB |

GPU 없이 CPU만으로 돌리는 환경입니다. 저 정도 크기의 모델이라면 충분히 돌아갑니다.

## 일단 속도부터 보자

모델을 로드하고 간단한 질문부터 던져봤습니다.

```
프롬프트: "Hello! Can you tell me what 2+2 is?"
응답: "Sure! 2 + 2 = 4. Let me know if you'd like to explore more math! 😊"
```

첫인상은 꽤 괜찮았습니다. 응답도 자연스럽고, 무엇보다 **빠릅니다.**

| 항목 | 수치 |
|------|------|
| 프롬프트 처리 (입력) | ~106 tokens/sec |
| **텍스트 생성 (출력)** | **~37 tokens/sec** |
| 모델 로드 | 0.09 ~ 0.5초 |

짧은 답변은 **1~2초**, 문단 수준의 답변도 **3~4초** 안에 나옵니다. GPU 없는 ARM CPU에서 이 정도면 체감상 거의 즉답에 가까운 느낌이에요.


## 350M이 얼마나 똑똑할까?

속도가 빠른 건 좋은데, 결국 중요한 건 **얼마나 똑똑하냐**입니다.<br>
claude를 통해 지능 테스트를 위한 다양한 난이도의 문제를 10개 던져봤습니다.

참고로, 여기서 결과에 대한 정리와 일부 코멘트는 claude가 작성해준 내용입니다.

### 쉬운 문제는 잘 합니다

```
Q: What is the capital of France? (프랑스의 수도는?)
A: Paris
```

```
Q: If a train travels 120km in 2 hours, what is its average speed?
   (기차가 2시간에 120km를 갈 때 평균 속도는?)
A: 120 km / 2 hours = 60 km/h ✅
```

기본적인 상식과 간단한 수학은 문제없이 맞춥니다. 간단한 코드 생성도 꽤 잘 합니다.

```
Q: Write a Python function that checks if a string is a palindrome.
   (문자열이 회문인지 확인하는 Python 함수를 작성해줘.)
A: def is_palindrome(s):
       return s == s[::-1]
```

간결하고 정확합니다. 350M이 큰 문제없이 이 정도면 초경량모델치고 꽤 놀랍습니다.

### 함정 문제 테스트

```
Q: A farmer has 17 sheep. All but 9 die. How many sheep are left?
   (농부에게 양 17마리가 있다. 9마리를 제외하고 모두 죽었다. 양은 몇 마리 남았는가?)
A: 17 - 9 = 8 ❌ (정답: 9)
```

"All but 9"를 "9마리가 죽었다"로 해석해버렸습니다. 영어 표현의 뉘앙스를 정확히 파악하지 못합니다.

```
Q: Sally has 3 brothers. Each brother has 2 sisters. How many sisters does Sally have?
   (Sally에겐 남자 형제가 3명 있다. 각 형제에겐 여자 형제가 2명 있다. Sally의 자매는 몇 명인가?)
A: 3 × 2 = 6 ❌ (정답: 1)
```

전형적인 논리 함정에 그대로 빠집니다. Sally 본인이 자매 중 한 명이라는 걸 이해하지 못하네요.

### 마음 이론 (Theory of Mind) 테스트

```
Q: I left my keys in the kitchen. Then I moved them to the bedroom.
   Then my wife moved them to the living room without telling me.
   Where do I think my keys are?
   (나는 열쇠를 부엌에 뒀다. 그 후 침실로 옮겼다.
   그 후 아내가 나 모르게 거실로 옮겼다. 나는 열쇠가 어디에 있다고 생각할까?)

A: The most logical conclusion is that your keys are in the living room ❌
   (가장 논리적인 결론은 열쇠가 거실에 있다는 것입니다)
```

요즘 들어 유행하는 LLM 테스트 중 하나입니다. 그 주유소 가는데 주유소가 걸어서 1분이야 뭐시기 하는 그런거입니다!<br>
아무튼 정답은 **"침실"**입니다. "내가 생각하기에"라는 관점을 이해하지 못하고 객관적 사실만 답합니다.<br>
이건 사실 큰 모델들도 종종 틀리는 문제이긴 하지만, 350M은 아예 개념 자체를 이해하지 못하는 느낌이었습니다.

### 인지 반사 테스트

```
Q: If it takes 5 machines 5 minutes to make 5 widgets,
   how long would it take 100 machines to make 100 widgets?
   (5대의 기계가 5분에 5개의 위젯을 만든다면, 100대의 기계가 100개를 만드는 데 얼마나 걸릴까?)
A: 5 minutes ✅
```

이 문제는 유명한 인지 반사 테스트(CRT) 문제인데, 사람들도 "100분"이라고 직관적으로 틀리는 경우가 많습니다. 350M이 이걸 맞췄습니다. 신기하네요

## 프로그래밍 관련 테스트

### 1. 학습 데이터가 많은 언어 (Python, js)

**Q: "Write a Python function that reads a JSON file and returns all keys that have null values."**
(JSON 파일을 읽어서 값이 null인 키들만 반환하는 Python 함수를 작성해줘.)

```python
import json

def get_null_keys(json_file):
    with open(json_file, 'r') as file:
        data = json.load(file)
        return [key for key in data if data[key] is None]
```

**완벽합니다.** `json.load` → `is None` 체크 → 리스트 컴프리헨션. 간결하고 정확한 코드입니다.

**Q: "Write a JavaScript function that debounces another function with a given delay in milliseconds."**
(주어진 밀리초 딜레이로 다른 함수를 디바운스하는 JavaScript 함수를 작성해줘.)

```javascript
function debounce(func, delay) {
  let timeoutId;
  return function(...args) {
    clearTimeout(timeoutId);
    timeoutId = setTimeout(func, delay);
    return args;
  };
}
```

구조는 맞지만 **`func`에 `args`를 전달하지 않는 문제**가 있습니다. `setTimeout(func, delay)`가 아니라 `setTimeout(() => func(...args), delay)`여야 합니다. 또한 `return args`도 일반적인 debounce 구현에선 불필요합니다. 아쉽지만 큰 틀은 맞췄습니다.

### 2. 학습 데이터가 적은 언어 (C++)

**Q: "Write a C++ function that implements a thread-safe singleton using std::call_once."**
(std::call_once를 사용해서 thread-safe한 싱글톤을 C++로 구현해줘.)

```cpp
static Singleton& getInstance() {
    std::call_once(
        [this] {
            // Initialization code
        },
        std::mutex::under_read
    );
    return *this;
}
```

**완전히 틀렸습니다.** `std::call_once`의 인자 순서도 잘못됐고(`once_flag`가 첫 번째여야 함), `std::mutex::under_read`라는 존재하지 않는 API를 만들어냈습니다. static 함수에서 `this`를 쓰는 것도 오류입니다.

반면 **템플릿 메타프로그래밍 팩토리얼**은 잘 작성했습니다.

**Q: "Write a C++ compile-time factorial using template metaprogramming."**
(템플릿 메타프로그래밍으로 C++ 컴파일 타임 팩토리얼을 작성해줘.)

```cpp
template <size_t N>
struct Factorial {
    static constexpr auto value = N * Factorial<N - 1>::value;
};

template <>
struct Factorial<0> {
    static constexpr auto value = 1;
};
```

이건 **정확합니다.** 재귀 템플릿 + base case 특수화까지 교과서적인 구현이에요. 아마 학습 데이터에 이 패턴이 많이 있었을 겁니다.

### 3. 설계/아키텍처 질문

**Q: "I have a REST API that handles user registration, login, and profile updates. Should I put all of these in one controller or separate them?"**
(REST API에서 회원가입, 로그인, 프로필 수정을 하나의 컨트롤러에 넣을지 분리할지?)

> **답변**
> You should separate your REST API into individual controllers for better organization, maintainability, and scalability. Here's why:
>
> 1. **Separation of Concerns**
>    - Each controller handles a specific domain, such as user registration, login, and profile updates. This makes the API more modular and easier to understand.
>
> 2. **Reusability**
>    - Each controller can handle different resources or operations, making it easier to reuse code and logic across the API.
>
> 3. **Scalability**
>    - Larger applications benefit from clean, focused controllers. Separating concerns allows you to scale individual parts independently.
>
> 4. **Maintainability**
>    - As the API grows, new features can be added without disrupting existing code. Each controller can be updated independently.
>
> 5. **Error Handling**
>    - It becomes easier to implement centralized error handling that applies to all requests.
>
> 6. **Testing**
>    - Unit tests can be written for each controller separately, making it simpler to test individual functionality.
{: .prompt-info }

**올바른 답변입니다.** 관심사 분리(SoC)를 중심으로 설계 원칙을 잘 설명했어요. 350M이 이 수준의 아키텍처 답변을 내놓는 건 인상적입니다.

**Q: "When should I use the Observer pattern vs the Pub/Sub pattern? What are the key differences?"**
(Observer 패턴 vs Pub/Sub 패턴은 언제 써야 하고, 핵심 차이는 뭔가?)

> **답변**
> **1. When to Use Observer Pattern:**
> - **Simple data flow**: When you have a few independent components that need to react to changes in a shared state without direct communication.
> - **Real-time updates**: Observers are ideal for scenarios where updates should be delivered asynchronously.
> - **Event-driven design**: Observers act as event listeners, allowing components to react to new data events without being tightly coupled.
>
> **2. When to Use Pub/Sub Pattern:**
> - **Message-based communication**: Pub/Sub is designed for sending messages between topics.
> - **Decoupling**: Pub/Sub promotes loose coupling between components.
> - **Global state management**: Pub/Sub can be used to share data across multiple components or services without tight coupling.
>
> **Key Differences:**
>
> | Feature | Observer Pattern | Pub/Sub Pattern |
> |---|---|---|
> | **Primary Use Case** | Reactive, event-driven updates | Message-based communication |
> | **Communication Model** | Direct observer-to-observer (async) | Topic-to-topic (publish/subscribe) |
> | **State Management** | Can be stateful (easier to manage) | Typically stateless (publish-only) |
> | **Scalability** | Easier to add/remove observers | Easier to add/remove topics/subscribers |
{: .prompt-info }

비교표까지 작성하며 **핵심 차이(직접 결합 vs 중간 브로커)를 잘 잡았습니다.** 다만 Observer에서 "observer-to-observer"라고 한 부분은 정확히는 "subject-to-observer"가 맞아서 용어가 약간 부정확합니다.

### 4. 같은 질문을 한국어로 하면?

**Q: "파이썬으로 JSON 파일을 읽어서 값이 null인 키들만 반환하는 함수를 작성해줘."**

```python
def get_null_key_values(file_path):
    with open(file_path, 'r') as file:
        data = json.load(file)
        return [key for key in data if key != 'null']
```

**영어로 물어봤을 때는 `data[key] is None`으로 정확했는데, 한국어로 물어보니 `key != 'null'`로 바뀌었습니다.** 키의 값이 null인지 확인하는 게 아니라 키 이름이 문자열 'null'이 아닌 것을 필터링하고 있어서 완전히 다른 로직이 되어버렸습니다.

**Q: "C++에서 std::call_once를 사용해서 thread-safe한 싱글톤을 구현해줘."**

```cpp
static std::call_once(Singleton::flag, threadSafeMethod);
```

영어 버전도 틀렸지만 한국어 버전은 **더 심하게 틀렸습니다.** `std::call_once`를 `static` 변수 선언처럼 쓰고 있고, 싱글톤 인스턴스를 반환하는 로직 자체가 없습니다. 한국어 설명은 자연스러웠지만 코드는 컴파일조차 되지 않습니다.

> - **관심사 분리(Separation of Concerns)**: 특정 기능을 관리하기 위한 작은 단위로 분리 가능합니다.

> - **보안 분리**: 로그인 로직과 프로필 처리를 분리함으로써 불필요한 복잡성을 줄일 수 있습니다.
>
> ### 2. **분리된 컨트롤러의 다방면적 이점**
> - **비즈니스 컨텍스트 분리**: 각 컨트롤러는 별도의 데이터베이스와 상호작용하는 역할을 합니다.
> - **API의 명확한 구조**: 각 기능의 의도와 책임을 명확하게 정의할 수 있습니다.
> - **보안 강화**: 인증과 보안(예: 비밀번호, 세션정보)을 별도로 처리하여 보안을 강화할 수 있습니다.
