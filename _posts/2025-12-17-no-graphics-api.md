그래픽스 API와 셰이더 언어는 지난 10년간 크게 복잡해졌습니다. 30년 경력의 그래픽스 프로그래머 Sebastian Aaltonen은 현대 GPU 하드웨어의 발전을 고려할 때, 추상화를 제거하고 개발을 단순화하며 성능을 개선할 때가 되었다고 주장합니다. 이 글에서는 DirectX 12, Vulkan, Metal 같은 "모던" API가 사실은 13년 전 하드웨어를 위해 설계되었으며, 현재 GPU 아키텍처에 맞춰 재설계한다면 훨씬 단순해질 수 있다는 점을 역사적 맥락과 함께 설명합니다.

## 저수준 그래픽스 API가 바꾼 산업

10년 전, 실시간 컴퓨터 그래픽스 분야에 큰 변화가 있었습니다. AMD는 Xbox One(2013)과 PlayStation 4(2013) 계약을 모두 따냈고, 새로운 Graphics Core Next(GCN) 아키텍처는 AAA 게임 개발의 사실상 표준 플랫폼이 되었습니다.

당시 PC 그래픽스 API인 DirectX 11과 OpenGL 4.5는 **드라이버 오버헤드가 크고 싱글 스레드 렌더링을 위해 설계**되어 있었습니다. AAA 개발자들은 PC를 위한 더 높은 성능의 API를 요구했고, DICE는 AMD와 함께 PC용 저수준 AMD GCN 전용 API인 Mantle을 만들었습니다. 이에 대응하여 Microsoft, Khronos, Apple은 자체적인 저수준 API를 개발하기 시작했습니다. 그렇게 DirectX 12, Vulkan, Metal이 탄생했습니다.

그러나 초기 반응은 엇갈렸습니다. 합성 벤치마크와 데모에서는 상당한 성능 향상을 보여줬지만, Unreal이나 Unity 같은 주요 게임 엔진에서는 성능 향상을 확인할 수 없었습니다. Ubisoft에서는 기존 DirectX 11 렌더러를 DirectX 12로 포팅하면 **오히려 성능이 저하되는 경우**가 자주 발생했습니다.

기존 고수준 API는 최소한의 지속 상태(persistent state)를 가지고 있었고, 세밀한 상태 설정자(state setter)와 개별 데이터 입력이 드로우 콜 제출 직전에 셰이더에 바인딩되었습니다. 새로운 저수준 API는 사전에 셰이더 파이프라인 상태와 바인딩을 지속 객체로 묶어서 드로우 콜을 더 저렴하게 만드는 것을 목표로 했습니다.

당시 GPU 아키텍처는 매우 이질적이었습니다. 데이터 재매핑, 검증, 업로드를 사전에 수행하는 것은 큰 이득이었습니다. 하지만 기존 게임 엔진의 렌더링 하드웨어 인터페이스(RHI)는 **세밀한 즉시 모드 렌더링을 위해 설계**되었고, 새로운 저수준 API는 데이터를 지속 객체로 묶어야 했습니다.

이 비호환성을 해결하기 위해, RHI 아래에 새로운 저수준 그래픽스 재매핑 레이어가 추가되었습니다. 이 레이어는 이전에 OpenGL과 DirectX 11 그래픽스 드라이버가 처리하던 복잡성을 떠맡았습니다. 그래픽스 프로그래머는 두 가지 역할로 전문화되기 시작했습니다. 새로운 저수준 "드라이버" 레이어와 RHI에 집중하는 저수준 그래픽스 프로그래머와, RHI 위에서 시각적 그래픽스 알고리즘을 구축하는 고수준 그래픽스 프로그래머입니다.

## "모던" API는 정말 현대적인가?

DirectX 12, Vulkan, Metal은 종종 "모던 API"라고 불립니다. 하지만 이 API들은 이제 10년이 되었고, **13년 전 GPU를 지원하도록 설계**되었습니다. GPU 역사에서 13년은 엄청나게 긴 시간입니다.

오래된 GPU 아키텍처는 오늘날 일반적인 컴퓨트 집약적 범용 워크로드보다는 전통적인 버텍스와 픽셀 셰이더 작업에 최적화되어 있었습니다. 벤더별 바인딩 모델과 데이터 경로가 있었고, 하드웨어 차이점을 동일한 API로 래핑해야 했습니다. 사전 생성된 지속 객체는 매핑, 업로딩, 검증, 바인딩 비용을 오프로드하는 데 중요했습니다.

반면 콘솔 API와 Mantle은 AMD의 GCN 아키텍처만을 위해 설계되었습니다. GCN은 당시로서는 선진적인 설계였습니다. **완전한 읽기/쓰기 캐시 계층**과 텍스처 및 버퍼 디스크립터를 저장할 수 있는 스칼라 레지스터를 가지고 있어, 모든 것을 메모리로 취급했습니다. 데이터를 재매핑하기 위한 복잡한 API가 필요하지 않았고, 사전 작업도 훨씬 적게 필요했습니다. 콘솔 API와 Mantle은 단일 현대적 GPU 아키텍처를 대상으로 했기 때문에 API 복잡성이 훨씬 낮았습니다.

10년이 지난 지금, GPU는 크게 진화했습니다. **모든 현대 GPU 아키텍처는 이제 코히런트 last-level 캐시를 갖춘 완전한 캐시 계층을 제공**합니다. CPU는 PCIe REBAR 또는 UMA를 통해 GPU 메모리에 직접 쓸 수 있고, 64비트 GPU 포인터가 셰이더에서 직접 지원됩니다. 텍스처 샘플러는 바인드리스이며, CPU 드라이버가 디스크립터 바인딩을 구성할 필요가 없습니다. 텍스처 디스크립터는 GPU 메모리 내 배열에 직접 저장될 수 있습니다(흔히 디스크립터 힙이라고 함).

만약 오늘날 현대 GPU를 위해 API를 설계한다면, 이러한 지속 "보유 모드(retained mode)" 객체 대부분이 필요하지 않을 것입니다. DirectX 12.0, Metal 1, Vulkan 1.0이 해야 했던 타협은 더 이상 필요하지 않습니다. **API를 대폭 단순화**할 수 있습니다.

지난 10년은 모던 API의 약점을 드러냈습니다. **PSO(Pipeline State Object) 순열 폭발**이 가장 큰 문제입니다. Valve, Nvidia 등 벤더들은 각 아키텍처/드라이버 조합마다 테라바이트의 PSO를 저장하는 대규모 클라우드 서버를 운영합니다. 사용자의 로컬 PSO 캐시 크기는 100GB를 초과할 수 있습니다. 게이머들이 로딩 시간이 오래 걸리고 스터터가 심하다고 불평하는 것도 당연합니다.

## GPU와 API의 역사

API 표면을 제거하는 것에 대해 이야기하기 전에, 그래픽스 API가 역사적으로 왜 이렇게 설계되었는지 이해해야 합니다. OpenGL이 의도적으로 느린 것도, Vulkan이 의도적으로 복잡한 것도 아닙니다. 10-20년 전에는 GPU 하드웨어가 매우 다양하고 빠르게 진화하고 있었습니다. 이렇게 다양한 하드웨어를 위한 크로스 플랫폼 API를 설계하려면 타협이 필요했습니다.

3dFX Voodoo 2 12MB(1998)는 3칩 설계였습니다. 단일 래스터라이저 칩이 4MB 프레임버퍼 메모리에 연결되어 있고, 두 개의 텍스처 샘플링 칩이 각각 4MB 텍스처 메모리에 연결되어 있었습니다. 지오메트리 파이프라인도 프로그래머블 셰이더도 없었습니다. CPU가 사전 변환된 삼각형 버텍스를 래스터라이저에 보냈고, 래스터라이저는 버텍스 색상과 두 텍스처 샘플러 결과를 결합하는 방식을 제어하는 설정 가능한 블렌딩 방정식을 가지고 있었습니다.

텍스처 샘플러는 서로의 메모리나 프레임버퍼를 읽을 수 없었습니다. 따라서 **다중 렌더 패스 지원이 없었습니다**. 하드웨어가 윈도우 합성을 할 수 없었기 때문에, 전용 2D 비디오 카드에 연결하는 루프백 케이블이 있었습니다. 3D 렌더링은 전체 화면 모드에서만 작동했습니다.

Nvidia의 GeForce 256은 GPU라는 용어를 만들었습니다. 래스터라이저 외에 지오메트리 프로세서를 가지고 있었습니다. 지오메트리 프로세서, 래스터라이저, 텍스처 샘플링 유닛이 모두 같은 다이에 통합되어 메모리를 공유했습니다. DirectX 7은 두 가지 새로운 개념을 도입했습니다. 렌더 타겟 텍스처와 유니폼 상수입니다. 멀티패스 렌더링은 텍스처 샘플러가 래스터라이저 출력을 읽을 수 있다는 것을 의미했고, 이는 3dFX Voodoo 2의 분리된 메모리 설계를 무효화했습니다.

DirectX 11이 등장하면서 데이터 모델에 큰 변화가 있었습니다. 컴퓨트 셰이더, 범용 읽기-쓰기 버퍼, 간접 드로잉 지원이 추가되었습니다. GPU는 이제 스스로를 완전히 피드할 수 있었습니다. 범용 버퍼의 포함으로 셰이더 프로그램이 프로그래머블 메모리 위치에 접근하고 수정할 수 있게 되었고, 이는 하드웨어 벤더들이 **범용 캐시 계층을 구현**하도록 강제했습니다.

셰이더는 단순한 1:1 데이터 변환을 넘어 진화했고, 전문화된 하드코딩된 데이터 경로의 시대가 끝났습니다. GPU 하드웨어는 범용 SIMD 설계로 전환하기 시작했습니다. SIMD 유닛은 이제 모든 다른 셰이더 타입을 실행했습니다: vertex, pixel, geometry, hull, domain, compute. 오늘날 프레임워크에는 16개의 서로 다른 셰이더 진입점이 있습니다. 이는 많은 API 표면을 추가하고 구성을 어렵게 만듭니다.

## 현대적 GPU 메모리 관리

레거시 그래픽스 API는 GPU 메모리 관리를 완전히 추상화했습니다. 오래된 GPU는 분할된 메모리 및/또는 다양한 캐시 일관성 문제가 있는 특수 데이터 경로를 가지고 있었기 때문에 추상화가 필요했습니다. DirectX 12와 Vulkan이 10년 전 등장했을 때, GPU 하드웨어는 사용자에게 배치 힙(placement heap)을 노출할 만큼 성숙했습니다.

현대 API는 사용자가 힙 타입을 열거하여 GPU 드라이버가 어떤 종류의 메모리를 제공하는지 확인하도록 요구합니다. 메모리를 큰 청크로 미리 할당하고 사용자 영역 할당자를 사용하여 서브할당하는 것이 좋은 관행입니다.

오늘날 CPU는 GPU 메모리에 대한 완전한 가시성을 가지고 있습니다. 통합 GPU는 UMA를 가지고 있고, 현대 디스크릿 GPU는 PCIe Resizable BAR를 가지고 있습니다. **전체 GPU 힙을 매핑**할 수 있습니다.

CUDA는 GPU 메모리 할당을 위한 단순한 디자인을 가지고 있습니다. GPU malloc API는 크기를 입력으로 받아 매핑된 CPU 포인터를 반환합니다. GPU free API는 메모리를 해제합니다. CUDA는 CPU 매핑 GPU 메모리를 지원하지 않습니다.

저자는 CUDA malloc 디자인과 CPU 매핑 GPU 메모리(UMA/ReBAR)를 결합할 것을 제안합니다. 이는 양쪽의 장점을 모두 취합니다. **데이터는 CPU가 쓰기에 빠르고 GPU가 읽기에도 빠르면서**, 깔끔하고 사용하기 쉬운 디자인을 유지합니다.

```c
// 1024개 uint32 배열을 위한 GPU 메모리 할당
uint32* numbers = gpuMalloc(1024 * sizeof(uint32));

// 직접 초기화 (CPU 매핑 GPU 포인터)
for (int i = 0; i < 1024; i++) numbers[i] = random();

gpuFree(numbers);
```

기본 gpuMalloc 정렬은 16바이트(vec4 정렬)입니다. 더 넓은 정렬이 필요한 경우 `gpuMalloc(size, alignment)` 오버로드를 사용합니다. GPU 메모리에 데이터를 직접 쓰는 것은 드로우 인자, 유니폼, 디스크립터 같은 작은 데이터에 최적입니다.

큰 영구 데이터의 경우에는 여전히 복사 작업을 수행하고 싶습니다. GPU는 캐시 지역성을 개선하기 위해 Morton 순서와 유사한 스위즐 레이아웃으로 텍스처를 저장합니다. 모든 현대 GPU는 **무손실 델타 컬러 압축(DCC)**도 가지고 있습니다. 현대 GPU의 복사 엔진은 DCC 압축 및 압축 해제가 가능합니다.

## 현대적 데이터 처리

CUDA, Metal, OpenCL은 64비트 포인터 시맨틱을 갖춘 C/C++ 셰이더 언어를 활용합니다. 이러한 언어는 적절하게 정렬된 모든 GPU 메모리 위치에서 구조체의 로드 및 저장을 지원합니다. 컴파일러는 **와이드 로드(combine), 레지스터 매핑, 비트 추출을 포함한 최적화**를 백그라운드에서 처리합니다.

많은 현대 GPU는 레지스터의 8/16비트 부분을 추출하기 위한 무료 명령어 수정자를 제공하여, 컴파일러가 8비트 및 16비트 값을 단일 레지스터에 패킹할 수 있게 합니다. 이는 셰이더 코드를 깔끔하고 효율적으로 유지합니다.

8개의 32비트 값으로 구성된 구조체를 로드하면, 컴파일러는 두 개의 128비트 와이드 로드(각각 4개의 레지스터를 채움)를 발행할 가능성이 높습니다. 이는 로드 명령어 수를 4배 감소시킵니다. 와이드 로드는 특히 구조체에 좁은 8비트 및 16비트 필드가 포함된 경우 훨씬 빠릅니다.

GPU는 ALU가 밀집되어 있고 큰 레지스터 파일을 가지고 있지만, CPU에 비해 메모리 경로는 상대적으로 느립니다. CPU는 종종 각각 사이클당 로드를 수행하는 두 개의 로드 포트를 가지고 있습니다. 현대 GPU에서는 **4사이클당 하나의 SIMD 로드**를 달성할 수 있습니다. 셰이더에서 와이드 로드 + 언팩은 종종 데이터를 처리하는 가장 효율적인 방법입니다.

전통적으로 컴팩트한 8-16비트 데이터는 DirectX 게임에서 텍셀 버퍼(Buffer<T>)에 저장되었습니다. 현대 GPU는 컴퓨트 워크로드에 최적화되어 있습니다. 요즘 원시 버퍼 로드 명령어는 텍셀 버퍼보다 최대 2배 높은 처리량과 최대 3배 낮은 지연 시간을 가집니다. **텍셀 버퍼는 더 이상 현대 GPU에서 최적의 선택이 아닙니다.**

## 현대적 바인딩과 디스크립터

DirectX 12와 Vulkan이 등장했을 때, 기존 GPU 하드웨어는 바인드리스 리소스를 광범위하게 지원하지 않았습니다. API는 하드웨어 차이점을 추상화하기 위해 복잡한 바인딩 모델을 채택했습니다. DirectX는 스테이지당 최대 128개의 리소스 인덱싱을 허용했고, Vulkan과 Metal은 처음에는 디스크립터 인덱싱을 전혀 지원하지 않았습니다.

AMD GCN(2012)은 스칼라 레지스터(SGPR)에 텍스처와 버퍼 디스크립터를 저장할 수 있는 최초의 GPU 중 하나였습니다. 각 웨이브는 102개의 SGPR을 가지고 있고, 각 디스크립터는 4-8 SGPR을 차지했습니다. **간단한 계산으로도 모든 디스크립터를 로드할 수 없다는 것**을 알 수 있었습니다. Nvidia Maxwell(2014)과 Pascal(2016)도 유사한 제한이 있었습니다.

Vulkan 1.2(2020)에서 드디어 **VK_EXT_descriptor_indexing**이 핵심으로 승격되었습니다. 그러나 여전히 복잡한 디스크립터 세트와 업데이트 모델을 유지했습니다. Vulkan의 VK_EXT_descriptor_buffer(2022) 확장은 저자의 제안과 유사하며, 사용자가 디스크립터를 표준 GPU 버퍼에 직접 쓸 수 있게 합니다.

현대 GPU에서는 다음과 같은 단순한 바인딩 모델이 가능합니다.

```c
// 텍스처 디스크립터 배열을 GPU 메모리에 직접 할당
TextureDescriptor* textures = gpuMalloc<TextureDescriptor>(1024);

// CPU에서 직접 쓰기 (매핑된 메모리)
textures[0] = createTextureDescriptor(texture0);
textures[1] = createTextureDescriptor(texture1);

// 셰이더에서 직접 인덱싱
color = textures[materialId].sample(uv);
```

디스크립터 세트, 레이아웃, 업데이트 같은 복잡한 API가 사라집니다. **모든 것이 단순히 메모리**입니다.

## 현대적 배리어

전통적인 그래픽스 API는 이미지 레이아웃 전환과 복잡한 배리어를 요구했습니다. 하지만 현대 GPU는 **코히런트 last-level 캐시**를 가지고 있어 대부분의 레이아웃 전환이 불필요합니다.

Vulkan은 최근 VK_KHR_unified_image_layouts(2025) 확장을 추가했습니다.[^unified-layouts] 이는 이미지 레이아웃 전환을 제거합니다. 텍스처가 DCC 압축된 상태로 업로드되면, 텍스처 샘플러와 디스플레이 엔진이 압축된 데이터를 직접 읽을 수 있습니다. 후속 데이터 레이아웃 변환이 필요하지 않습니다.

저자는 단순한 배리어 모델을 제안합니다.

```c
// 쓰기 후 읽기 배리어만 필요
gpuBarrier(commandBuffer, WRITE_AFTER_READ);
```

대부분의 경우 GPU 하드웨어가 자동으로 캐시 일관성을 처리하므로, 명시적 배리어가 최소화됩니다.

## 현대적 셰이더 언어

HLSL과 GLSL은 **프레임워크 스타일 디자인**을 채택했습니다. 각 셰이더 호출은 단일 데이터 요소(버텍스 또는 픽셀)에서 작동했습니다. 이는 당시 하드웨어 차이를 추상화하는 좋은 방법이었지만, 오늘날에는 확장성 문제를 보이고 있습니다.

CUDA, Metal, OpenCL은 C/C++ 기반 셰이더 언어를 사용하며, 64비트 포인터와 구조체를 완전히 지원합니다. 라이브러리 생태계가 번창합니다. 저자는 그래픽스 셰이더도 이러한 접근 방식을 채택해야 한다고 주장합니다.

```c
// 현대적 메쉬 셰이더 스타일
void meshShader(uint groupId) {
    Mesh* mesh = meshes[groupId];

    // 직접 메모리 접근, 포인터 사용
    for (uint i = 0; i < mesh->vertexCount; i++) {
        Vertex v = mesh->vertices[i];
        // 변환 및 출력
    }
}
```

프레임워크 진입점 대신 **일반적인 C 함수**를 사용하면 코드 재사용과 라이브러리 개발이 훨씬 쉬워집니다.

## 마치며

30년 경력의 그래픽스 프로그래머가 제안하는 이 비전은 급진적으로 보일 수 있지만, 사실은 하드웨어의 자연스러운 진화를 따르는 것입니다. 13년 전 이질적인 GPU 아키텍처를 위해 설계된 복잡한 API는 오늘날 범용 SIMD, 완전한 캐시 계층, 64비트 포인터를 갖춘 현대 GPU에는 더 이상 필요하지 않습니다.

**PSO 순열 폭발, 100GB 캐시, 긴 로딩 시간, 스터터**는 모두 과도한 추상화의 증상입니다. Vulkan조차 VK_EXT_descriptor_buffer, VK_KHR_unified_image_layouts 같은 확장으로 단순화의 길을 걷고 있습니다.

저자가 제안하는 단순한 API는 CUDA의 명확성과 현대 GPU의 메모리 매핑 기능을 결합합니다. `gpuMalloc`으로 메모리 할당, 포인터로 직접 접근, 최소한의 배리어, C/C++ 기반 셰이더 언어. 이것이 현대 GPU 하드웨어를 위한 "No Graphics API"의 핵심입니다.

그래픽스 프로그래밍은 복잡할 필요가 없습니다. 하드웨어가 단순해졌다면, **API도 단순해져야 합니다**.

## Quick questions

> **DirectX 12와 Vulkan은 왜 이렇게 복잡하게 설계되었나요?**
>
> 10년 전 등장했을 때 다양한 GPU 아키텍처(AMD, Nvidia, Intel, 모바일)를 모두 지원해야 했기 때문입니다. 당시 하드웨어는 서로 다른 바인딩 모델과 데이터 경로를 가지고 있었고, 이를 공통 API로 추상화하려면 복잡한 디스크립터 세트, PSO, 레이아웃 전환 같은 개념이 필요했습니다.

{: .prompt-info}

> **현대 GPU는 무엇이 달라졌나요?**
>
> 모든 주요 벤더(AMD, Nvidia, Intel, Apple, Qualcomm)가 이제 범용 SIMD 아키텍처, 코히런트 last-level 캐시, 64비트 포인터, 바인드리스 리소스를 지원합니다. 하드웨어가 수렴했기 때문에 과거처럼 복잡한 추상화가 더 이상 필요하지 않습니다.

{: .prompt-info}

> **왜 텍셀 버퍼보다 원시 포인터 로드가 빠른가요?**
>
> 텍셀 버퍼는 텍스처 샘플러 하드웨어를 거치며 타입 변환과 포맷 확장을 수행합니다. 이는 레이턴시를 추가하고 와이드 로드를 방해합니다. 반면 원시 포인터 로드는 L1 캐시에서 직접 읽어 최대 2배 높은 처리량과 3배 낮은 레이턴시를 제공합니다.
